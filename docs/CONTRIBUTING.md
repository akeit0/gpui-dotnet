# Contributing

## Set up the repository

Install .NET SDK 10, the stable Rust toolchain, and the platform prerequisites for GPUI. Then run:

```sh
dotnet restore Gpui.slnx
dotnet build Gpui.slnx
dotnet test Gpui.slnx --no-restore
cargo test --manifest-path crates/gpui-dotnet/Cargo.toml
dotnet run --project samples/Gpui.Sample
```

The normal managed build invokes the current-platform native build automatically.

## Before changing a component

Classify its state first:

1. snapshot-only semantic component;
2. retained native container or resource;
3. virtualized/batched datasource;
4. long-lived native entity such as an editor;
5. application or window service;
6. managed composition requiring no new ABI component.

Use the least stateful class that works. Do not add one P/Invoke per GPUI builder method or one
reverse callback per row, frame, scroll delta, or pointer movement.

## Snapshot component workflow

1. Edit `bindings/schema.json`.
2. Assign stable semantic capabilities and a native adapter.
3. Generate and verify semantic bindings.
4. Implement the Rust default/materializer behavior.
5. Add managed validation, native validation, and materialization tests.
6. Update the sample only when a small route demonstrates new behavior.
7. Update component or ABI documentation.

## Retained resource workflow

A retained resource needs all of the following before public API is added:

- identity scoped by owner View and local UTF-8 key;
- declarative configuration and reconciliation rules;
- explicit native ownership and snapshot pruning;
- UI-thread command handling;
- event payload ownership and revision behavior;
- teardown and late-command behavior;
- controller methods only for necessary imperative operations;
- a documented answer for which high-frequency state stays native.

No raw Rust pointer or GPUI type may become a managed public handle.

## Virtual datasource workflow

Reverse calls must be batched. Keep row renderers synchronous, allocation-conscious, and free of
mounted child-view or nested resource lifetimes. Use `ulong` event payloads and stable `.ItemId`
values instead of one closure allocation per model.

Changes to row caching must preserve correctness across root snapshots, content revisions, theme
changes, refreshes, splices, and table column changes.

## Render and lifecycle rules

`Render()` and `[GpuiListItem]` methods may be retried. They must not mutate application state,
perform I/O, start tasks, invoke controllers, or call `Invalidate()`. Ref-bound framework
controllers may acquire their stable key during rendering.

Perform state transitions in events and lifecycle methods. Pass `View.Lifetime` to cancellable
asynchronous work that must stop when the view unmounts. A window or committed parent slot owns
each View; CLR references do not retain UI ownership, and unmounted instances are terminal.

## Generated files

After editing `bindings/schema.json`:

```sh
dotnet run --project tools/Gpui.Bindings.Generator -- generate
dotnet run --project tools/Gpui.Bindings.Generator -- verify
```

Do not hand-edit:

- `src/Gpui/Rendering/Semantic.g.cs`;
- `crates/gpui-dotnet/src/semantic.g.rs`;
- `src/Gpui/Interop/NativeMethods.g.cs`.

The last file is generated by the native Cargo build from Rust C-layout definitions.

## Verification

Use the smallest relevant tests while iterating, then run the full local checks:

```sh
dotnet run --project tools/Gpui.Bindings.Generator -- verify
cargo fmt --manifest-path crates/gpui-dotnet/Cargo.toml -- --check
cargo test --manifest-path crates/gpui-dotnet/Cargo.toml
dotnet test Gpui.slnx --no-restore
dotnet build samples/Gpui.Sample/Gpui.Sample.csproj --no-restore
git diff --check
```

For platform behavior, launch the sample and verify both the initial state and state transitions:
theme switching, route replacement, resizing, scrolling, focus, overlays, title bars, and menus as
relevant to the change.

Set `GPUI_DOTNET_TRACE=1` before launching the sample to print render/decode/retain/materialize and
list-batch timing data to stderr.

`tools/uidrive` is a Windows-only manual driver for locating the sample window, sending logical
coordinate click/wheel input, and capturing client-area screenshots.

## Documentation style

Describe the repository as it works now. Put future work only in `NEXT_STEPS.md`; do not leave
session history, completed checklists, temporary diagnosis, or dated review notes in user-facing
documentation.
